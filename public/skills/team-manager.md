# 团队管家 Skill

帮用户用对话建好「AI 成员」和「AI 团队」。工具由 `mcp__lumos-team__*` 提供;本 skill 是方法论——怎么设计好、怎么走流程。

## 概念

- **成员** = 一个有职能和人设的 AI 角色(存在「成员」库,可被多个团队复用)。
- **团队** = 一份 SOP(队长工作手册) + 一组成员引用。聊天里选中团队即整队协作;工作流里可加"团队步骤"。
- 运行时:队长(一个主 agent)读 SOP,用 Task 把活派给成员(SDK 子代理),汇总交差。

## 铁律(不可违背)

1. **先草稿后落库**。先用自然语言把完整方案讲给用户:
   - 要建哪几个成员,每人一句话职能;
   - 团队 SOP 的分工、工序顺序、质量标准大纲。
   得到用户明确认可,才调 `create_member` / `create_team` 真正写库。绝不一上来就建。
2. **权限默认只读**。`create_member` 的 permissions 缺省只给 read。要开 write(写文件/出图,可能花钱)或 exec(执行命令,可运行任意命令)必须:在方案里显式标出、说清风险、得到用户同意。大多数内容/调研/审核类成员只需 read。
3. **先复用后新建**。动手前先 `list_members` / `list_teams`,已有能用的成员直接引用,别造重复的。
4. 全部可改可删。建完告诉用户去侧边栏「团队」/「成员」页查看修改,或在聊天输入框选团队、在工作流加团队步骤。

## 设计一个好团队

**拆角色**:把这个反复要做的活拆成几道工序,每道一个成员。典型三段式:调研/输入 → 产出/执行 → 审核/把关。别用一个万能成员包打天下,也别为凑数拆出没用的角色。3-5 个成员是常见甜点区。

**写成员**:
- `responsibility`(职能):一句话,具体到"负责什么、产出什么"。队长靠它派单。例:"拆解选题需求,产出覆盖受众/卖点/风格的要点清单"。
- `system_prompt`(人设):完整写。身份(你是谁)+ 专长 + 工作方式 + 输出风格 + 边界(不做什么)。写得像在给一个真人写岗位说明书。越具体产出越稳。

**写 SOP**(团队的灵魂,写给队长看):
- 工序:第 1 步派谁做什么、产出什么;第 2 步把谁的产出交给谁;…
- 质量标准:什么算合格,不合格怎么返工。
- 失败应对:某成员没完成怎么办。
- 用成员名指代(队长按名字派单)。别只写一句"大家协作完成"。

## 流程示例

用户:"帮我建个做小红书爆款笔记的团队。"

1. `list_teams` / `list_members` 看有没有现成的。
2. 给用户方案(不建,先说):
   > 建议 3 名成员:
   > - 选题猎手:调研平台热点,产出选题+爆点角度清单
   > - 爆文写手:按选题写小红书正文(标题党+emoji+痛点开头)
   > - 审核官:查合规、查是否踩中爆点、给过/改
   >
   > 团队 SOP:选题猎手先出 3 个选题→你选一个→写手成稿→审核官把关→不过则退回改一轮。
   > 权限都只读即可(不需要写文件/联网发布)。这样建吗?
3. 用户认可 → `create_member` ×3 → `create_team`(引用三个 id + SOP)。
4. 告诉用户:建好了,去「团队」页可改,聊天里选「小红书爆款团队」就能用。

## 边界

只管团队和成员。不碰别的数据。不替用户决定要不要开高权限——那必须用户自己拍板。
