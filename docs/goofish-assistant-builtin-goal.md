# Lumos 用户侧内置级应用生成器目标：以闲鱼助手为首个验证样板

**状态**：Draft v4
**日期**：2026-05-07
**主目标**：让用户在正常使用 Lumos 时，可以用自然语言生成、安装、配置、运行和迭代“内置级应用”，而不是要求开发者手工修改 Lumos 源码。
**验证样板**：`闲鱼助手`。闲鱼助手不是唯一目标，而是用来验证这套用户侧应用生成机制是否能做出接近官方内置应用质量的复杂业务应用。

## 1. 关键纠偏

这次目标不是“我们现在开发 Lumos 源码时提速”，而是：

- 用户在 Lumos 里说“帮我做一个闲鱼助手”。
- Lumos 先把需求拆成应用规格、用户故事、权限、数据、自动化、AI 助手、IM 命令和验收清单。
- Lumos 基于受控运行时生成一个可安装应用包。
- 用户能在 `应用` 页看到它、打开它、配置它、运行它、测试它，并继续通过对话迭代它。

这类应用不应直接叫“官方内置应用”。更准确的边界是：

- `官方内置应用`：随 Lumos 版本发布，由 Lumos 核心代码提供，例如现有微信助手。
- `内置级应用`：用户在 Lumos 内生成，复用官方应用壳、状态合同、AI 助手、自动化、IM、通知、数据模板和验收模板，但业务逻辑运行在受控应用运行时里。
- `需要官方核心能力的部分`：如果某个需求需要新增底层驱动、系统权限、原生桥接或未开放 API，Lumos 不能伪装成已经完成，只能生成能力缺口说明、开发任务或等待官方能力发布。

## 2. 下一阶段 Goal 描述

建立 `用户侧内置级应用生成器`：

- 用户用自然语言描述应用需求。
- Lumos 生成应用规格和可验收范围，先让用户确认关键边界。
- Lumos 生成并安装可运行的原生应用包，不要求用户打开源码工程。
- 生成应用自动复用 Lumos 的应用入口、页面壳、状态区、设置页、AI 助手、提示词、统一 AI 对话框、自动化、运行结果、IM 通知、IM 命令和验收清单。
- 高风险动作默认禁止或必须用户确认。
- 应用缺少底层能力时，必须在 UI 和验收清单里明确显示“未接入 / 需授权 / 需官方能力”，不能用假数据冒充完成。

判断这个 goal 是否有效，不是看“闲鱼助手是否一次生成所有功能”，而是看：

- 用户是否能不改代码地创建一个可打开、可配置、可运行、可测试的闲鱼助手。
- 第二个类似应用是否能复用同一套生成器、运行时、页面壳、AI 助手、自动化、IM 和验收模板。
- 生成应用时，Lumos 主要补“业务配置 / 业务适配器 / 能力声明”，而不是每次重新发明入口、状态、设置、列表、详情、AI 对话框、自动化、通知、命令和错误处理。

## 3. 不能走的路

为了保证用户机器安全和产品质量，第一阶段不做：

- 不让 AI 生成任意 TypeScript 后直接在 Lumos 主进程或 Next 服务端执行。
- 不绕过应用包校验、权限声明、安装确认和自检。
- 不把未接入的底层能力包装成“已完成”。
- 不让 IM 自然语言命令直接执行高风险操作。
- 不让生成应用获得未声明的文件、网络、IM、浏览器或系统权限。

生成应用第一阶段应尽量运行在已有 `lumos-app` 受控运行时、应用 SDK、Workflow、AI 工具、DeepSearch、IM provider 和已审查 capability 之上。

## 4. 提速来自哪里

### 4.1 固定生成规格

每个内置级应用都应先生成一份可检查规格：

- 应用名、目标用户、核心场景。
- 页面结构：概况、列表、详情、设置、自动化、结果。
- 数据集合：业务实体、设置、草稿、通知、命令记录、用户标记。
- 权限声明：AI、Workflow、DeepSearch、IM、浏览器、文件、网络。
- 风险边界：只读、低风险写、高风险写、必须确认动作。
- 验收清单：用户可以在 UI 里逐项验证。

规格先于代码和文件生成，避免模型直接拼 UI。

### 4.2 固定应用入口和页面壳

生成应用不应每次重写应用列表、打开按钮和基础状态。

应沉淀：

- 应用 registry：声明 id、名称、图标、入口、能力标签、状态接口。
- 应用列表自动渲染卡片。
- 统一 `未配置 / 需授权 / 同步中 / 已就绪 / 失败 / 未接入` 状态。
- 通用页面壳：概况、列表、详情、设置、自动化、运行结果。
- 通用 loading、empty、error、retry 和权限缺失状态。

### 4.3 固定 API / 数据 / 状态合同

生成应用应优先声明合同，再由运行时提供通用实现：

- `status`：依赖、登录、数据、同步、通知、AI 配置状态。
- `settings`：读取、保存、校验、默认值。
- `list / detail / search`：分页、筛选、错误格式。
- `draft / confirm`：AI 建议和用户确认分离。
- `runs / events`：后台任务、自动化、IM 命令和用户操作记录。
- `notifications`：通知目标、发送状态、失败原因。
- `user_marks`：备注、星标、待处理、忽略。

业务模块只新增自己的核心实体，不重复造辅助表。

### 4.4 固定应用级 AI 助手

每个高质量应用都需要应用内 AI，但不应每个应用单独搭。

应沉淀：

- 统一 AI 对话框：底部入口、消息流、加载态、失败态、重试和附件展示。
- 应用级 assistant service：把当前应用状态、选中对象、最近记录和用户问题注入上下文。
- 提示词模板：默认 system prompt、输出格式、风险边界、禁止事项。
- 提示词设置页：用户可编辑角色、语气、输出要求、模型参数。
- AI 草稿机制：AI 先生成建议或草稿，用户确认后才执行写操作。
- 工具轨迹：用户能看到 AI 基于哪些对象生成建议。

### 4.5 固定自动化 / 定时任务

生成应用常见自动化应复用同一套能力：

- 启用、暂停、立即运行、编辑、删除。
- 每天、每周、每 N 小时、一次性时间等普通表单。
- Workflow / schedules 接入模板。
- 运行中、成功、失败、取消、失败原因、重试入口。
- 自动化报告预览、完整弹窗、下载、跳转执行记录。
- 生命周期收口：删除或关闭自动化必须取消运行中的执行。

### 4.6 固定 IM 通知和 IM 命令

很多应用都会需要“主动通知用户”和“用户从微信下命令”。

应沉淀：

- 应用级通知目标选择和测试。
- 统一默认 IM 发送封装。
- 应用级 IM 命令 router。
- 命令权限分级：只读、低风险写、高风险写。
- 命令执行记录和失败提示。
- 高风险命令必须二次确认或直接禁止。

## 5. 闲鱼助手作为样板要验证什么

闲鱼助手的目标不是孤立做一个官方内置应用，而是验证用户侧生成器能否生成一个“内置级”的复杂业务应用。

### 5.1 现有闲鱼业务底座

当前仓库已经具备：

- `goofish-cli` 安装检测和安装入口。
- 扫码 / 浏览器 / Cookie 三类登录方式。
- 多闲鱼账号目录和登录态管理。
- 闲鱼会话同步并写入本地 SQLite。
- 买家会话列表、聊天详情、消息发送。
- 本地消息 FTS 搜索。
- `getInbox` 一次性返回会话和最近消息，适合 AI 汇总。
- 商品搜索。
- MCP 工具暴露 `list accounts / inbox / list sessions / get messages / search chats / search items / sync`。
- AppBuilder 的能力清单已能声明受控 `goofish` 原生集成边界：读能力包括安装 / 状态 / 账号 / 同步 / 收件箱 / 会话 / 消息 / 搜索 / 商品查询；写能力第一阶段只允许“对明确会话发送文本消息且需要用户确认”；自动无确认回复、发布商品、改价、下架、删除和批量修改仍标为不可用 / 高风险。

这些是闲鱼助手可以调用的底层能力，不等于用户侧应用生成器已经完成。

### 5.2 闲鱼助手第一阶段产品能力

用生成器生成的闲鱼助手第一阶段应做到：

- 用户能在 `应用` 页看到并打开 `闲鱼助手`。
- 用户能完成闲鱼依赖安装、账号登录和同步状态检查。
- 用户能查看买家会话、商品上下文、最近消息和未读待处理项。
- 用户能让 AI 基于买家消息和商品上下文生成回复草稿。
- 用户确认后才发送闲鱼消息。
- 用户能配置微信 IM 通知目标，接收未读、需回复、同步失败和关键买家消息提醒。
- 用户能通过微信 IM 下达低风险命令，例如查看未读、查看最近消息、生成回复草稿、确认发送某条草稿、触发同步、查看状态。
- 用户能在闲鱼助手里打开统一 AI 对话框，询问当前未读、某个买家、某个商品或最近待回复事项。
- 用户能调整闲鱼助手提示词，例如回复风格、禁止承诺、议价边界、售后语气和输出格式。
- 用户能启用定时同步、定时检查未读、定时微信摘要和定时待回复列表。
- 商品管理第一阶段只做只读和低风险标记：商品搜索、商品上下文、备注、待处理标记。

## 6. 第一阶段明确不做

- 自动无确认回复买家。
- 自动发布商品。
- 自动改价。
- 自动下架或删除商品。
- 批量修改商品。
- 绕过闲鱼风控的浏览器自动化。
- 把微信 IM 自然语言命令直接解释为高风险写操作。
- 用户侧生成器自行实现新的闲鱼底层登录、同步或发送协议。

第一阶段原则：AI 可以生成草稿和建议；真正发给买家的消息必须用户确认。

## 7. 如何保证能用

### 7.1 生成应用可用门槛

每个生成应用至少必须满足：

- 入口卡片可见。
- 页面可打开。
- 状态区能显示未配置、未接入、已就绪和失败。
- 设置页可保存。
- 列表页有 loading、empty、error 和 retry。
- API 返回统一错误格式。
- AI 对话框能显示未接入、已接入和失败。
- 提示词设置能保存并被调用链读取。
- 自动化页能显示无任务、运行中、成功、失败和取消。
- 自动化关闭或删除符合任务生命周期规则。
- IM 通知测试能显示成功或失败原因。
- IM 命令能返回明确结果。
- 验收清单能在 UI 里逐项验证。

### 7.2 闲鱼助手就绪门槛

`闲鱼助手` 不能显示 `已就绪`，除非同时满足：

- 闲鱼运行依赖已安装。
- 至少一个闲鱼账号登录态有效。
- 最近一次同步成功，或明确返回“暂无会话”。
- 本地会话列表能加载。
- 如果开启微信通知，默认 IM provider 已配置，目标 chat 已保存，测试通知成功。
- 如果规格声明微信 IM 命令，每个声明的低风险命令都必须存在模板并完成成功测试；否则状态应显示 `未接入` 并指出缺少或尚未测试成功的命令。

### 7.3 回复发送门槛

`生成回复草稿` 可以失败并显示原因，但 `发送回复` 必须满足：

- 草稿绑定了明确闲鱼会话。
- 草稿绑定了明确接收方。
- 用户在 UI 或微信命令里明确确认。
- 发送后写入结果，失败时保留草稿。

## 8. 推荐实施顺序

1. 把现有 AppBuilder 的目标从“自由生成应用”收敛到“内置级应用生成”规格。
   - 当前已完成第一步代码收口：新增 `native-app-spec.json` 规格文件、schema 读取、模板生成和 AppBuilder 能力契约检查；项目状态页已能展示、编辑、保存校验、接受或标记需修改当前规格；安装前检查也已加入“规格确认”。最新又把该门禁从前端按钮禁用提升为服务端安装硬校验：缺少规格、规格无效、未接受当前规格或接受版本已过期时，`/api/apps/builder/sessions/<id>/install` 会拒绝安装；同时 AppBuilder `install_app` 工具执行前也会校验 `native-app-spec.json`，缺规格或规格无效时返回 `NativeSpecInvalid`，且在有 Builder 会话上下文时还会要求当前规格版本已被用户接受，避免 AI 工具绕过「项目状态」确认直接安装。直接保存或由 AI 工具循环更新 `native-app-spec.json` 时，规格确认状态也会自动回到 `待确认`。这只证明生成链路开始要求、展示并确认规格，且安装入口和工具路径不会轻易绕过内置级规格，不等于完整内置级应用生成主链已打通。
2. 继续完善 `native-grade app spec`：页面、数据、权限、AI、自动化、IM、验收清单，并把规格确认接到后续真实生成和自检链路。
3. 扩展应用模板和校验器，强制生成应用包含状态、设置、错误态、权限说明和验收清单。
   - 当前 starter 模板和本地草图已带第一版「状态 / 设置 / 自动化 / 通知命令 / 运行结果」页面，以及 `app_settings / app_automations / run_history / assistant_messages / app_notifications / app_command_runs / acceptance_checks` 通用集合。
4. 建通用应用壳：概况、列表、详情、设置、自动化、运行结果、底部 AI 对话框。
   - 当前已有第一版状态、设置、自动化定义、通知命令模板、运行结果页面壳和已安装应用底部 AI 对话框；自动化页已有手动运行桥但尚未接真实定时调度 bridge；通知命令页可记录通知目标、命令模板、风险等级和执行结果，应用到默认微信 IM 通知与 `/goofish status / unread / sync` 外部微信斜杠命令已有第一版受控路径；完整列表/详情标准态、工具化 AI 草稿确认链、通用 IM 入站模板和应用直聊仍未完成。
5. 建通用状态 service 合同和 UI 映射。
   - 当前已有第一版 `/api/apps/<id>/status` 和已安装应用顶部状态条，可显示 `未配置 / 已就绪 / 运行中 / 失败 / 未接入`。
   - 最新已把状态判定继续收紧到闲鱼助手样板的真实就绪门槛：闲鱼类应用不会仅因保存过设置就显示 `已就绪`，还必须能看到已同步的闲鱼账号状态、至少一个登录可用账号、最近一次同步成功；声明自动化时会检查 `system.schedule` 权限，声明 IM 命令时会按规格逐个检查低风险命令模板和成功测试记录，缺少 `/status`、`/runs` 这类模板或某个命令尚未测试成功时都会明确显示 `未接入` 原因，避免旧逻辑在桥已接上后仍固定报“未接入”，也避免只测试一个命令就误报整个 IM 命令能力已就绪。最新又把 `/goofish draft <conversation>`、`/goofish confirm <draft>`、`/goofish reject <draft>` 这类带参数命令按命令族识别，已有具体命令记录时不会再被误报为模板缺失，但仍要求命令族至少有一次成功测试记录才算就绪。状态 service 和顶部状态条也已开始展示验收进度和验收异常数量；当存在多个未接入原因时，顶部状态条会在主提示下方额外列出更多缺口，减少只看到第一条原因的误判。
6. 建应用级 AI 助手模板：提示词设置、上下文注入、AI 草稿、用户确认。
   - 当前底部 AI 对话框会读取最近 30 条对话、保存用户/助手/错误消息，并把应用状态、验收进度、提示词和风险边界注入 `/api/apps/<id>/ai/complete`；最新已补第一版通用上下文注入，会把最近运行结果、验收记录、自动化状态和 IM 命令状态带入应用助手；同时已补第一版受控自检动作，用户问“检查应用是否可用 / 重新验收 / 生成自检证据”时，AI 只能返回 `run_self_check` 动作块，界面展示“运行安装自检”按钮，点击后走 `native:app:run-self-check` 并把结果写回对话和 `run_history`；动作卡现在会显示受控动作名称、建议原因、执行状态和风险说明，AI 助手保存回复草稿成功或失败也会额外写入 `run_history`。这仍不是完整的应用级工具助手。
   - 当前已新增闲鱼类应用的第一版上下文注入和受控草稿动作：AI 助手会读取最近的 `buyer_conversations / reply_drafts / item_marks` 摘要作为上下文；AI 回复可附带 `create_reply_draft` 动作块，界面只显示“保存回复草稿”按钮；用户点击后才把草稿写入应用隔离数据 `reply_drafts`。该能力只基于应用内已有数据保存本地草稿，不代表已接通真实闲鱼同步或发送。
   - 当前已新增闲鱼助手买家会话行级草稿生成入口：用户在 `买家会话` 页点击某条会话的“生成回复草稿”，后端会读取该行买家、商品、最近消息、备注、商品标记和应用提示词 / 风险边界，优先调用当前文本生成服务商生成草稿；服务商不可用或返回空时降级为保守模板草稿。结果只保存到 `reply_drafts`，写入草稿编号和 24 小时确认有效期，并写入 `run_history`，不会发送给买家。这是第一版受控草稿生成，不代表草稿质量、多轮议价策略、微信 IM 确认发送或自动化回复已经完整闭环。
7. 建安装后验收清单 UI：读取规格中的验收项，允许用户逐项记录验收进度。
